# Задача A — Ingest: план оптимизации

Дата: 2026-10-30. Область: только Track A. Это план экспериментов; реализация baseline не меняется.

Основа: [общая стратегия](optimization-strategy-2026-10-30.md),
[исследование](optimization-research-2026-10-29.md),
[проверки baseline](../tests/BASELINE_VALIDATION.md).
Утверждения о правилах и размерах входа взяты из этих документов; перед реализацией
специализаций нужно сверить их с зафиксированной актуальной официальной спецификацией.

## Цель и исходное состояние

Ускорить полный запуск при точном совпадении `summary.txt` с Python reference.
Выбирать варианты по совокупности времени, пиковой памяти, размера исходников и зависимостей.
По умолчанию сохранять ноль внешних зависимостей.

Сейчас `track-a/src/main.rs` выполняет всё последовательно:

- `BufReader::lines()` выделяет строку на каждую запись;
- `split(' ').collect()` создаёт временный вектор полей;
- ключ `(String, String)` заново выделяется даже для существующей группы;
- каждая группа хранит собственный `Vec<u32>`, затем полностью сортируется через `sort()`;
- ключи групп сортируются отдельно, вывод идёт через `BufWriter` и `writeln!`.

Baseline прошёл tiny/sample на seeds 1, 7, 42, full на seed 1 и явные крайние случаи.
2.88 с на VPS — единственный correctness run с запуском Docker, а не достоверный
performance baseline. Обещать коэффициент ускорения пока нельзя.

## Порядок работ

Каждый шаг — отдельный сравнимый эксперимент. Следующий шаг строится на принятом варианте.

| Шаг | Изменение | Что проверяем | Условие принятия |
|---|---|---|---|
| A0 | Повторяемый baseline; диагностические таймеры parse/group, percentiles, output в stderr | Где тратятся время и память | Сохранены исходники, условия и все повторные измерения |
| A1 | Отдельно проверить `lto`, `codegen-units=1`, `panic="abort"`; затем CPU flags | Выигрыш только от сборки | Корректность и воспроизводимое улучшение полного запуска |
| A2 | Переиспользуемый буфер строки; итератор полей вместо `collect()` | Цена временных аллокаций | Улучшение T без ухудшения суммарного результата |
| A3 | `mmap` и безопасный байтовый парсер в одном потоке; сначала сохранить прежнюю агрегацию | Чтение, копирование, парсинг | Точные байты; измерены T и cgroup memory.peak |
| A4 | Интернирование endpoint, компактный hour ID, плотные группы; сначала стандартный `HashMap` | Цена ключей, хеширования и множества объектов | Выигрыш с учётом памяти и размера кода |
| A5 | Сравнить векторы групп с потоком `(group_id, latency)` и общей arena | Локальность против дополнительного прохода и временной памяти | Победа по полному запуску и пику памяти |
| A6 | Сначала `sort_unstable`; затем каскадный `select_nth_unstable` для больших групп | Нужно ли полностью сортировать latency | Лучший порог на sample/full, без ошибок совпадающих рангов |
| A7 | Параллельный parse/group с локальным состоянием; слияние словарей и групп | Масштабирование с учётом merge | Лучший общий результат для 1/2/4/6/12 потоков на доступной машине |
| A8 | Параллельные percentiles/output по диапазонам часов; затем отдельный опыт с форматированием чисел | Новый bottleneck после ускорения ingest | Время всего процесса уменьшается достаточно, чтобы окупить код и память |

`target-cpu=native` проверять отдельно: бинарник должен собираться на целевом CPU;
не переносить такой бинарник с более нового процессора. Изменения Dockerfile должны
сохранять автономную сборку и закреплённые образы.

## Целевая форма после проверки гипотез

1. Read-only mapping входа; срезы endpoint живут не дольше mapping.
2. Байтовый парсер возвращает час, endpoint, latency и признак 5xx.
3. Локальные словари endpoint и локальные данные workers, без общей блокировки на запись.
4. После чтения — объединение endpoint и назначение глобальных ID в байтовом порядке.
5. Глобальный `group_id = hour_id * endpoint_count + endpoint_rank` задаёт порядок вывода.
6. Точные перцентили по данным каждой непустой группы; вывод строго по group ID.

Это направление, а не требование реализовать всё сразу. Пользовательская hash table,
SWAR/SIMD, PGO и ручное форматирование остаются резервом до подтверждения bottleneck.
Более простой вариант сохраняется, если он даёт лучший итоговый результат.

## Риски, которые нужно закрыть

- Число endpoint определяется из входа; не зашивать каталог seed 1 или размер 1842.
- Индекс на 72 часа допустим только после подтверждения диапазона дат в контракте;
  иначе сохранить общий календарный ключ. Проверить смену месяца и крайние часы.
- Вход перемешан: нельзя закрывать группу или час по порядку прихода записей.
- Latency включает `0` и `u32::MAX`; точные значения, без приближённых квантилей и histogram по узкому диапазону.
- Для непустой группы индекс nearest rank: `ceil(p*n/100)-1`. При совпадении рангов
  повторно использовать значение; не передавать недопустимый индекс в укороченный срез.
- Ошибки — только 500–599; ppm = `errors * 1_000_000 / count` целочисленно, счётчик `u64`.
- Endpoint сравниваются полностью, включая длинные общие префиксы; при коллизии хеша
  обязательно сравнение байтов. Короткий префикс сортируется раньше длинного.
- Пустой файл, маленькие chunks, границы строк и конец mapping обрабатываются без выхода за срез.
- Merge суммирует все counts/errors и сохраняет все latency; порядок завершения workers не влияет на вывод.
- Для arena считать одновременно живущие pair buffers, capacities, arena, словари и output.
  Освобождение после пика не снижает уже измеренный memory.peak.

## Протокол проверки и выбора

После каждого изменения запускать существующую byte-for-byte матрицу из
`tests/README.md`: tiny/sample, seeds 1/7/42, явные edge cases. Для кандидата на
публикацию — full seed 1 и дополнительные seeds, включая не использованный для настройки.
Для chunking и selection добавить проверки именно их границ.

Производительность сравнивать на одном Linux x86-64 стенде, с одинаковыми CPU affinity,
лимитами контейнера и состоянием page cache. Apple ARM пригоден для разработки,
но его результаты не определяют выбор для scoring CPU. На 6-vCPU VPS отдельно
проверять oversubscription; оптимальное число потоков уточнить на целевом стенде.

На вариант — пять последовательных запусков, хранить все пять; итог — среднее
трёх после удаления min/max. При нестабильности сначала найти причину разброса.
Диагностические таймеры отключить в финальном замере. Время брать exec→exit;
не смешивать его с длительностью запуска Docker. Память — cgroup memory.peak,
а не только RSS. Поведение prewarm для mmap сверить с актуальным harness.

Карточка результата: revision/hash, seed/scale, CPU, compiler/image, build flags,
workers, SHA-256 вывода, пять T, итоговый T, M, S, D и расчёт score по текущему harness.
Локальные результаты хранить отдельно от официальных. В `track-a/PERF.md`
указывать реальные board run ID, не заменять их локальными измерениями.

## Готовность

План реализации начинается с A0–A2: получить надёжную точку отсчёта и проверить
дешёвое устранение аллокаций. Затем последовательно A3–A7; A8 — только по профилю.
Готовый кандидат проходит полную проверку, offline container build и ограничения
песочницы, имеет воспроизводимое улучшение и журнал измерений. Публикация на board
и отправка изменений выполняются отдельным действием.
