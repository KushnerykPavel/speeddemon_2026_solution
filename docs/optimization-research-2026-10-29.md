# Оптимизация Speed Demon 2026: треки A и D

Дата исследования: **29 октября 2026**, до открытия live board. Цель — выбрать следующие эксперименты для существующих Rust-решений. Это исследование источников и кода, а не результаты новых бенчмарков. Приоритеты ниже — инженерные гипотезы, которые нужно проверять на полном входе и нескольких seed.

## Короткий вывод

- **A:** специализированный байтовый разбор → словарь endpoint и числовой ключ группы → `sort_unstable` против точного multi-selection → параллельные блоки и локальное накопление.
- **D:** быстрый разбор чисел и проверки недостижимости по степеням → компактный CSR → переиспользуемые массивы расстояний → параллельные запросы → сравнение binary/radix heap и двунаправленного поиска.
- Сложные SIMD-парсеры, ALT и contraction hierarchies оставить до измерений простого варианта. Выигрыш времени должен окупать память, сложность и штраф за код/зависимости.

## Ограничения и критерий выбора

Стенд: шесть P-ядер / 12 аппаратных потоков, 8 GB без swap; build и запуск offline. Время включает ввод, предобработку и вывод. `mmap` разрешён, `io_uring` заблокирован. Native CPU build и PGO на данных генератора разрешены. Официальное время — среднее трёх средних из пяти запусков. Зависимости и превышение размера эталонного кода штрафуются. [Правила и scoring](https://speeddemon.dev/#scoring).

Для оценки вариантов использовать формулу с ограничениями факторов:

```text
K = (Tref/T)^0.50
  × min(Mref/M, 50)^0.20
  × min(Sref/S, 1)^0.15
  × (Dref/D)^0.15
D = 1 + число прямых runtime-зависимостей
```

Из неё следует наш расчёт: при одинаковой памяти и размере кода первая зависимость требует ускорения более `2^0.30 ≈ 1.231×`, то есть сокращения времени более чем на 18.8%, чтобы повысить K. Если учитываемый S удвоился выше порога эталона, получается такой же порог. Удвоение памяти вне области memory cap требует ускорения более `2^0.40 ≈ 1.320×`. Это пороги окупаемости, а не прогнозы.

## Общие эксперименты для обоих треков

1. **Сборка:** сравнить текущий release с `lto = "thin"`, `codegen-units = 1`; отдельно native CPU и при необходимости fat LTO. Это параметры для A/B-измерения, а не гарантированные ускорители. Разбор компромиссов есть у автора [Rust Performance Book](https://nnethercote.github.io/perf-book/build-configuration.html).
2. **PGO после стабилизации алгоритма:** instrument → несколько генераторных seed → merge profiles → rebuild с profile-use и теми же остальными флагами. Официальный [rustc PGO workflow](https://doc.rust-lang.org/rustc/profile-guided-optimization.html) описывает все четыре стадии. Не обучаться исключительно на одном seed; не включать готовые ответы или индекс конкретного входа.
3. **I/O:** сравнить большой повторно используемый буфер, `read_to_end` и `mmap`. Полная копия текста упрощает borrowed keys и разбиение по строкам, но повышает peak memory. `mmap` не означает бесплатную память: `memory.peak` отражает пик всей cgroup, а `memory.stat` отдельно учитывает файловый cache и mapped pages. [Документация Linux](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html#memory).
4. **Вывод:** после устранения основных затрат измерить форматирование чисел и запись. В A выход достаточно велик, чтобы учитывать его отдельной фазой; начинать с `BufWriter` и переиспользуемого текстового буфера. В D форматирование небольшого списка ответов — низкий приоритет.

## Трек A: разбор лога и точные агрегаты

### Что решаем

Официальный A — не общий CSV-парсер, а агрегирование HTTP-лога с одним пробелом между полями. Вход гарантированно ASCII, без кавычек, CR и пустых строк; timestamp имеет 27 байт. Нужны точные nearest-rank p50/p95/p99 и целочисленный error_ppm. Учитываются повторы; строки не отсортированы. Поэтому сложность общего CSV (quoting, multiline, dialect sniffing) можно целиком убрать. Каталог endpoint зависит от seed; его следует обнаруживать из входа. Это следует из [официальной спецификации A](https://github.com/hackathon-raptors/speed-demon-2026/blob/main/specs/a-ingest.md).

Ниже «предложение» означает вывод для этого проекта, а не измеренный прирост. Чужие GB/s не переносятся на scoring box.

### Приоритетный backlog A

P0 — первый эксперимент; P1 — после быстрого последовательного baseline; P2 — по оставшемуся профилю; P3 в D — исследовательский резерв. Это порядок работы, а не измеренная величина выигрыша.

Готовые dataframe/SQL-движки и CLI групповой статистики в A запрещены: например Polars, DuckDB, pandas, Arrow compute, xsv/qsv. Парсеры, selection, hash maps и SIMD helpers допустимы с учётом зависимости. Поэтому приведённые ниже публикации используются как источники методов, а не рекомендация запустить готовый аналитический движок. [Спецификация A, §6](https://github.com/hackathon-raptors/speed-demon-2026/blob/main/specs/a-ingest.md#6-banned-libraries).

#### A1 — убрать аллокации на каждой строке; P0, малая/средняя сложность

Предложение: сначала dependency-free streaming parser поверх `BufRead::fill_buf()`/переиспользуемого `read_until`, либо `fs::read()` + borrowed byte slices как отдельный A/B. Не собирать Vec полей; skip timestamp на фиксированные 27 байт, найти конец method, конец endpoint, по первой цифре трехзначного status определить 5xx, latency разобрать непосредственно из ASCII. Временную строку часа и owned endpoint создавать только при первом появлении, а не каждой строке. Метод не влияет на результат.

Принцип удаления validation/аллокаций подтвержден [автором rust-csv](https://burntsushi.net/csv/); `fs::read` возвращает весь файл в Vec<u8> по [стандартной документации](https://doc.rust-lang.org/std/fs/fn.read.html). Конкретная схема полей — наш вывод из грамматики A. Начать с scalar digit loop; SIMD и unsafe не нужны для первого шага.

Что измерить: end-to-end time, parsing/grouping phase, allocations, peak RSS. Whole-file path удерживает примерно весь input в памяти, streaming path экономит RSS; выбор зависит от полного score, а не только parse throughput. Нельзя хранить ссылку на переиспользуемый streaming buffer после следующего чтения: dictionary копирует только впервые встреченный endpoint либо хранит offsets в долгоживущем whole-file buffer.

#### A2 — intern endpoint и dense group IDs; P0, средняя сложность

Предложение: endpoint→small integer ID строить из входа; группу адресовать `endpoint_id * 72 + hour_id`. Для фиксированного 72-часового диапазона hour_id вычисляется из календарной даты+часа или из таблицы четырех дат. Нельзя брать только HH: одинаковые часы разных дней различаются. Имена endpoint оставить один раз, а не в каждом ключе. После чтения один раз получить endpoint IDs в byte-lexicographic порядке и выводить hours×sorted IDs, пропуская count=0. Это убирает повторное хэширование hour-строк и сортировку сотен тысяч строковых составных ключей.

Это проектный вывод, не утверждение из чужого benchmark. Его корректность опирается на [официальный контракт ключей и сортировки](https://github.com/hackathon-raptors/speed-demon-2026/blob/main/specs/a-ingest.md). Существующий `&timestamp[..13]` уже верен и его не нужно объявлять ошибкой: числовой ID — следующая оптимизация.

Оценка конструкции: 72×1842=132624 возможных групп. Только заголовки Vec<u32> при типичном 64-битном layout 24 bytes займут около3.18MB; counters добавят еще память. Сами 3.1M значений u32 —12.4MB без capacity slack. Это расчет предлагаемого представления, не измеренный RSS и не гарантия ABI. Endpoint-major адресация позволяет добавлять новые IDs без переадресации уже заполненных групп.

Улучшение при подтвержденном bottleneck: вместо многих маленьких Vec — два прохода: в первом посчитать groups, prefix sums, во втором заполнить единый latency arena. Выигрыш locality/аллокаций оплачивается вторым чтением/парсингом; не начинать с этого без профиля.

#### A3 — сначала sort_unstable, затем точный multiselect; P0/P1, малая/средняя сложность

Предложение: стабильность порядка одинаковых u32 не используется, поэтому `sort_unstable()` — дешевый первый эксперимент. После него сравнить гибрид: маленькие группы сортировать, большие — выбрать только три нужных rank через `select_nth_unstable()`. Размер порога подобрать на распределении текущего input, не копировать чужую константу. API дает in-place O(n) selection по [Rust docs](https://doc.rust-lang.org/std/primitive.slice.html#method.select_nth_unstable).

Для каждого p индекс `k=(p*n+99)/100-1`. Rank могут совпадать: вычислить уникальные индексы, выбирать с корректными offsets на непересекающихся subslices и сохранять найденные значения, иначе последующий selection может переставить предыдущую позицию. Например, сначала выбрать p50, затем p95 в правой части, затем p99 в оставшемся хвосте; совпадающий rank переиспользовать. Минимум n=1, повторяющиеся значения и max-u32 обязательны. Оценка O(n) для фиксированных трех ranks относится к алгоритму, а не обещает меньший wall time на коротких группах.

Не использовать t-digest, HDR/log histogram, DDSketch, reservoir sampling или округление: требуется точное значение из входа. Полная прямая гистограмма uint32 на группу неприемлема. Даже один массив из 2^32 счетчиков u32 равен16GiB; много групп только ухудшают ситуацию. Exact high-byte histogram/radix-select допустим теоретически как поздний вариант для огромных групп, но потребует нескольких проходов и собственного кода; сначала standard-library selection.

#### A4 — LF-aligned parallel chunks + local aggregation; P1, средняя/высокая сложность

Предложение: разделить input по byte ranges, каждую внутреннюю границу сдвинуть вперед к следующему LF и получить непересекающиеся `[boundary_i,boundary_{i+1})`; каждый worker сразу парсит и агрегирует. Не создавать общий locked HashMap и не материализовать список всех records. Для каждого worker — свой endpoint dictionary и groups, затем global remap локальных endpoint IDs, сложение counters и concatenation latency. Детерминированно сортировать только финальные ключи. Идея fused parse/accumulate/merge — из [VLDB2026](https://www.vldb.org/pvldb/vol19/p3579-ellmann.pdf), конкретное упрощение boundary — наш вывод из отсутствия quoted LF.

Оценить1/2/4/6/12 workers; hardware threads не гарантируют линейного выигрыша. Dense table на worker умножает metadata и capacity slack, возможен memory-score regress. При небольшом input выбрать serial path по измеренному crossover. Chunk size и worker count тюнить на целевой машине. Не полагаться на исходные восемь log shards: shard ID отсутствует и их disorder не дает streaming-watermark guarantees.

#### A5 — memchr/SIMD framing и SWAR numbers; P2 после профиля

Сравнить scalar scan, `memchr` и свой небольшой ISA-specific parser с безопасным fallback. [memchr docs](https://docs.rs/memchr/latest/memchr/) прямо различают throughput на больших buffers и latency на коротких строках: SIMD может проиграть для короткого method scan. При разработке SIMD нужен корректный tail; нельзя читать за границу буфера, полагаясь на «валидный input». Цель соревнования — i5-13500 с AVX2; локальные ARM-измерения не заменяют проверку x86-64.

Latency — единственное полноценное decimal число каждой строки; status можно проверить как byte `'5'`, дата/час — fixed digits. [SWAR8 Lemire](https://lemire.me/blog/2022/01/21/swar-explained-parsing-eight-digits/) применим только если numeric conversion действительно заметен в профиле. До10 digits: length-aware split8+tail или scalar fallback, без truncation до8 digits. Float parsers, fast_float и locale handling задаче не нужны.

#### A6 — финальный вывод и grouping memory; P2

У baseline уже есть buffered output; не приписывать ему per-line syscall без измерения. Если formatting становится существенным после A1–A4, попробовать крупный reusable byte output buffer и прямое integer encoding вместо многих formatter calls. Output порядка10MB может стать заметной долей субсекундного запуска. Сначала измерить, затем решать, стоит ли новый код/itoa dependency цены scoring. Это инженерная гипотеза для этого проекта.

### Где оптимизации ломают задачу

Дата на границе месяца, отсутствующие группы, empty input, endpoint prefix/byte ordering, endpoint125 bytes, произвольный 100..599 status, zero/max-u32 latency, n=1/2/101, duplicates и сильный disorder должны проходить побайтовое сравнение с эталоном. Нельзя hardcode endpoint catalogue из seed1, обрезать high latency по обычному распределению генератора, flush «старого» часа по ограниченному lateness либо дедуплицировать requests. [Generator](https://github.com/hackathon-raptors/speed-demon-2026/blob/main/generators/a_ingest.py) специально инъецирует редкие крайние значения: типичный диапазон не заменяет полный контракт.


## Трек D: точные кратчайшие пути

### Что определяет выбор алгоритма

**Факты условий.** Directed graph: 1 740 512 вершин, 5 000 000 дуг, 2 000 запросов. Плотные ID; веса `0..u32::MAX`; ответы могут превышать `u32`. Есть параллельные дуги, односторонние дороги, недостижимые вершины. Нормальные цели выбираются по Dijkstra rank: медиана 512, среднее около 12 300, максимум 131 071. Предобработка входит во время. Готовые shortest-path/index библиотеки запрещены; обычные очереди, radix heaps и параллельные runtimes разрешены. [Официальная спецификация, §§2,3,6](https://github.com/hackathon-raptors/speed-demon-2026/blob/main/specs/d-traverse.md).

**Факт генератора.** Основная часть — дорожная решётка с артериями и highways, случайная перестановка ID и перемешанные дуги. Поэтому ID не кодирует координаты. Генератор уже показывает хорошую технику: `rank_target` переиспользует массив расстояний, записывает изменённые ID в `touched`, затем сбрасывает только их. [Исходник генератора, `main_network`, `rank_target`](https://github.com/hackathon-raptors/speed-demon-2026/blob/main/generators/d_traverse.py).

**Наш вывод.** Это задача точного point-to-point поиска с преимущественно короткими запросами, а не обход всего графа и не поток миллионов дальних запросов. Вначале выгоднее убрать хеширование/аллокации и заведомо бесполезные поиски. Большой индекс должен оправдать стоимость построения за один запуск.

### Очередь экспериментов

Все строки — **наши предложения**, а не обещания ускорения. Последовательные варианты следует сравнивать на одинаковых данных и учитывать общее время загрузки, построения и ответов.

| Приоритет | Изменение к текущему Rust baseline | Почему подходит | Цена и проверка |
|---|---|---|---|
| P0 | До поиска: `s==t -> 0`; затем `outdegree(s)==0 || indegree(t)==0 -> -1` | Убирает невозможный поиск в основной компоненте при цели без входящих дуг | Проверять равенство первым. Самопетли могут ослабить, но не нарушить этот фильтр |
| P0 | `HashMap<usize,u64>` заменить на переиспользуемый `Vec<u64>` + touched list | ID плотные, каждое чтение расстояния становится индексированием | Инициализировать один раз; в touched добавлять при первом переходе из INF; не очищать все n элементов на запрос |
| P0 | Переиспользовать `BinaryHeap` и его capacity | Убирает повторные выделения памяти | Очищать оставшуюся очередь после раннего завершения; stale entries по-прежнему пропускать |

| P1 | Bidirectional Dijkstra | Расширяет два меньших фронта по исходному/reverse графу | Корректный stopping rule, два набора distance/touched/heap; на коротких запросах overhead может перевесить |

| P2 | `u64` radix heap против binary heap; опционально 4-ary heap | Неотрицательные целые веса дают монотонные извлечения | Не связывать корректность с типичными небольшими весами; zero и огромные веса обязательны |

Первые три шага не требуют нового алгоритма. Полезно сначала получить быстрый forward baseline, затем сравнить bidirectional и radix независимо: одновременная замена скроет источник выигрыша.

### Почему CSR, touched/stamps и reverse graph

CSR хранит offsets и массив дуг; обход соседей — contiguous range. Это документированная структура, а не предложение подключить запрещённую библиотеку. [Первичная документация Boost CSR](https://www.boost.org/doc/libs/latest/libs/graph/doc/html/graph/graph_classes/compressed_sparse_row.html).

**Наш расчёт для full, без capacity/allocator overhead:** `u32 offsets[n+1]` + `u32 head[m]` + `u32 weight[m]` ≈46,96 MB на направление; два направления ≈93,92 MB. Distance-массив `u64[n]` ≈13,92 MB на направление. Timestamps `u32[n]` добавят ≈6,96 MB. Двунаправленное worker state с distance+stamp ≈41,77 MB, плюс heaps; шесть workers ≈250,63 MB. У timestamp-варианта нет touched reset, но есть stamp check на каждом доступе и явная обработка переполнения generation. Это альтернативы для измерения, не две обязательные структуры одновременно.

**Наше предложение:** не сортировать весь файл ради CSR. Сохранить временные тройки или дважды разобрать вход; посчитать degrees, prefix sum, заполнить ranges. Параллельные дуги безопасно заменить минимумом на `(u,v)`, а self-loop удалить при неотрицательных весах, но это отдельный эксперимент: их мало и сортировка/хеширование для dedup может стоить дороже сэкономленного обхода.

### Двунаправленный поиск: что должно быть доказано

Обратный поиск идёт по **входящим** дугам исходного графа; нельзя трактовать сеть как неориентированную. Поддерживать `mu` — длину лучшего уже обнаруженного полного пути, обновляя через пересечения/дуги между поисками. **Наше условие реализации для обычной Dijkstra:** после удаления stale entries из вершин обеих очередей завершать при конечном `mu` и `min_forward + min_backward >= mu`. Не завершать при первом обнаруженном общем ID. Если один фронт исчерпан, вернуть найденное конечное `mu`, иначе `-1`; не принимать сравнение `INF+INF>=INF` за найденный путь. Все суммы в `u64`, INF выбран с запасом и не складывается без проверок.

Основа — двунаправленные алгоритмы и поддержание длины лучшего пути в работе Goldberg/Harrelson. Для A* там отдельно разобрано, почему независимые potentials требуют специального termination; обычное правило Dijkstra нельзя механически перенести на произвольный bidirectional A*. [Авторская публикация Microsoft Research, §§5–6](https://www.microsoft.com/en-us/research/wp-content/uploads/2005/01/soda05.pdf).

### Integer queues: актуально и применимо

Radix heap использует порядок целочисленных ключей и монотонность Dijkstra. Классическая работа даёт улучшенные оценки для ограниченных целых весов, но её теоретическую границу нельзя автоматически приписать любой lazy-duplicate реализации. [Ahuja, Mehlhorn, Orlin, Tarjan, 1990](https://www.princeton.edu/~alaink/Orf467F11/AhujaRadixHeap.pdf).

Есть небольшой Rust проект с документированной monotone queue, runtime code использует buckets и `leading_zeros`; `Reverse` поддерживается. Его структура по умолчанию — **max** heap, для minimum нужны `Reverse<u64>` ключи. Для Dijkstra делать ключом расстояние, а node хранить payload: zero-weight relaxation к меньшему ID может нарушить монотонность лексикографического `(distance,node)` ключа. [Репозиторий автора](https://github.com/mpdn/radix-heap), [исходник](https://github.com/mpdn/radix-heap/blob/master/src/lib.rs). Зависимость разрешена именно как data structure, но её стоимость/лицензию/вендоринг нужно учитывать.

**Archive.org проверен буквально.** В оцифрованном авторском MIT working paper *Network Flows* (1988), §3.2, Dial использует `C+1` buckets и имеет O(m+nC); авторы объясняют проблему большого C. [Полный текст Internet Archive](https://archive.org/stream/networkflows00ahuj/networkflows00ahuj_djvu.txt), [карточка оригинала](https://archive.org/details/networkflows00ahuj). **Наш вывод:** глобальная таблица на `u32::MAX+1` buckets здесь непригодна. Можно исследовать небольшое кольцо с отдельным overflow heap либо radix, но нельзя отбрасывать тяжёлые веса или полагать их отсутствующими. Исторические утверждения книги о «самом быстром на сегодня» не являются состоянием исследований 2026 года.

### ALT / CH: резерв, с проверкой окупаемости

ALT предвычисляет distances to/from landmarks и получает нижние границы по triangle inequality. [Оригинальная работа и страница авторов](https://www.microsoft.com/en-us/research/publication/computing-the-shortest-path-a-search-meets-graph-theory/). Для directed графа формула: `h(v,t)=max(0, d(L,t)-d(L,v), d(v,L)-d(t,L))` по выбранным L, только при определённых конечных расстояниях. **Наша рекомендация:** сначала обычный однонаправленный A* с доказанно допустимой/согласованной potential; для disconnected графа безопаснее применять ALT внутри проверенной SCC, используя общий поиск снаружи. Игнорирование INF-пар может нарушить consistency — тогда нужны reopening либо отдельное доказательство. Геометрический A* по node ID недопустим: координат на входе нет.

Инженерный блог GraphHopper показывает реальные режимы bidirectional/A*/landmarks/CH и сложность доведения landmarks до production. Его коэффициенты ускорения относятся к другому движку, данным и маршрутам, поэтому **не переносим их в прогноз**. [Блог разработчика, 2017](https://www.graphhopper.com/blog/2017/08/14/flexible-routing-15-times-faster/).

RoutingKit документирует медленное preprocessing CH и быстрые запросы, отдельное query state на поток. Это полезный образец архитектуры для чтения, **сам RoutingKit и готовые builders запрещены**. [Документация проекта](https://github.com/RoutingKit/RoutingKit/blob/master/doc/ContractionHierarchy.md). Дополнительно его исходник задаёт 32-bit `unsigned` и `inf_weight=2147483647u`, что несовместимо с диапазоном D без переделки. [constants.h](https://github.com/RoutingKit/RoutingKit/blob/master/include/routingkit/constants.h).

**Наш break-even test:** сохранять индекс только если `T_preprocess + sum(T_index_query) < sum(T_fast_Dijkstra_query)` с воспроизводимым запасом и лучшим общим score. Для k directed landmarks нужны 2k full SSSP, а таблицы `u64` занимают `16*k*n` bytes: k=4 ≈111,39 MB, k=8 ≈222,79 MB. Сравнивать с реальным количеством посещённых вершин после дешёвых фильтров, а не с Python reference. Отдельно измерять дальние запросы, но выбирать победителя по всему набору.

### Что нового на arXiv и почему это не первая реализация

Проверены первичные работы: [Duan et al., 2025, *Breaking the Sorting Barrier*](https://arxiv.org/abs/2504.17033), deterministic directed SSSP O(m log^(2/3)n); и [Duan et al., 2026, *A Faster Directed Single-Source Shortest Path Algorithm*](https://arxiv.org/abs/2602.07868), улучшение до O(m√(log n)+√(mn log n log log n)), для sparse graphs O(m√(log n log log n)). Это действительно более свежее состояние теории, чем один только результат 2025 года. **Наш вывод:** данные результаты решают SSSP по всем вершинам и сами по себе не доказывают практического превосходства для короткого point-to-point D, малых integer weights и ограниченного размера решения. Пока backlog P3, не заменять ими измеряемый простой алгоритм.

### Минимальные проверки каждого эксперимента

`s==t` на изолированной вершине; directed one-way; zero path; параллельные дуги обоих порядков; duplicate query; max-u32 и сумма двух огромных весов; остров→main; main→no-in target; одинаковые minimum keys; stale entries; повторное использование state после раннего выхода; исходный порядок ответов при parallel completion. Эти проверки проверяют конкретные риски оптимизаций, а не только совпадение seed-1 hash.

## Оценки памяти до реализации

Это наши арифметические оценки полезных массивов, не измерения RSS/cgroup и не гарантии фактического layout Rust.

| Структура | Расчёт для full | Что не включено |
|---|---|---|
| A: все latency как `u32` | `3,100,000 × 4 = 12.4 MB` | Ёмкости Vec, ключи, счётчики, allocator |
| A: плотная таблица групп | `72 × 1,842 = 132,624` ячейки; при 32 B/ячейку ≈4.24 MB | Сами значения, словарь endpoint; при параллельных таблицах умножить overhead на workers |
| D: один CSR | `(n+1) × 4 + m × 8 ≈46.96 MB` | Рабочие курсоры, входной текст, временные рёбра, allocator |
| D: forward + reverse CSR | ≈93.92 MB | Предобработка и рабочие массивы |
| D: `u64 dist + u32 stamp` | `n × 12 ≈20.89 MB` на worker и направление | Heap, settled state и служебные буферы |
| D: шесть forward workers | ≈125.32 MB только dist/stamp | Общий CSR и переменные размеры heap; bidirectional удвоит эту часть |

Для CSR здесь предполагаются отдельный массив `u32 offsets` и рёбра `(u32 target, u32 weight)` по 8 B: счётчик 5 млн рёбер помещается в `u32`. Индексацию срезов приводить к `usize`. Суммы расстояний оставлять `u64`. Вариант с `usize offsets` занимает больше; это тоже допустимый кандидат, если удобство или скорость окупают память.

Главный практический вывод: хранение всех latency A само по себе недорого; покупать экономию памяти приблизительными квантилями не нужно. Для D важно считать **одновременно живущие** входной текст, временные тройки рёбер, CSR, reverse CSR и массивы workers. Освобождение временных буферов после пика не уменьшает уже зафиксированный peak.

## Как проверить гипотезы

### Протокол

1. Зафиксировать хеш исходников, compiler/image digest, настройки сборки, seed/scale и машину. Сначала получить повторяемый Rust baseline.
2. Для каждого изменения выполнить существующую проверку byte-for-byte с Python: tiny/sample на 1, 7, 42, явные edge cases; финалистам — full на нескольких seed, включая ранее не использованный. Не подбирать алгоритм по готовому хешу seed 1.
3. Замерять отдельно диагностические фазы: A — чтение/parse/group, percentiles, output; D — parse, build CSR/reverse/preprocess, queries, output. Диагностический режим пишет только в stderr; итоговый T брать снаружи процесса.
4. Для сравнения производительности использовать один Linux x86-64 стенд, одинаковую привязку CPU, лимиты и состояние прогретого page cache; пять последовательных запусков, среднее после удаления min/max. Сохранить все пять, не только выбранное число.
5. Собирать peak memory тем же механизмом, что harness, плюс S, D и K. В D дополнительно: settled/relaxed, heap pushes/pops, stale pops, доля загрузки; в A: аллокации/строка, размеры групп, время квантилей и слияния.
6. Менять один фактор за эксперимент. После каждого принятого изменения повторно профилировать: при ускорении поиска D загрузка может стать главным потребителем времени, а при ускорении A парсинга — запись или квантили.
7. В `PERF.md` вносить измерение с реальным board run ID, когда board открыт; локальные эксперименты обозначать локальными. Доказательства baseline уже хранятся в `tests/`, новые результаты сохранять отдельно.

| Трек | Варианты | Решающий показатель |
